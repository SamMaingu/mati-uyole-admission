4. Application State Machine

draft  payment_pending  paid  submitted  under_review
    additional_info_required (loop back to under_review)
    eligible / not_eligible
    selected / waitlisted / not_selected
    admission_completed

Enforce transitions server-side (a small state-machine class or Laravel enum + policy), not just in the frontend -- e.g. reject any request to submit an
application whose payment status isn't paid .

6. Integration Abstraction Interfaces

Define these as interfaces/contracts from day one, even with a stub/manual implementation underneath -- this is what makes future API integration a
swap, not a rewrite.

   interface PaymentServiceContract {
          public function generateControlNumber(Application $application): string;
          public function checkStatus(string $controlNumber): PaymentStatus;
          // Option A (manual): checkStatus reads from a manually-updated `payments` row
          // Option B (GePG): checkStatus calls the GePG API / handles their webhook

   }

   interface SmsServiceContract {
          public function send(string $phone, string $templateKey, array $data): void;

   }

   interface AcademicVerificationContract {
          public function verifyIndexNumber(string $indexNo): VerificationResult;
          // Stub returns "unverified -- manual" until NECTA/NACTVET API access exists

   }

Bind these in a Laravel service provider so swapping the underlying implementation is a one-line config change.

8. UI / Design Direction -- Clean & Minimalistic

Since the brief calls for very clean, minimalistic design, keep these principles in front of whoever builds the React screens:

         One accent color, used sparingly -- e.g. a single green (echoing agriculture/MATI branding) for primary actions and status badges.
         Everything else stays neutral (white/off-white background, dark grey text, light grey borders).
         Generous white space over dense forms. The multi-step flow (Account  Personal  Academic  Payment  Programme  Review) should
         be one step per screen, not one long scrolling form -- this matches "student asijazwe form ndefu" from the requirements doc directly.
         Progress indicator (simple stepper, not a percentage bar) so the applicant always knows where they are and what's left.
         Typography: one clean sans-serif family (e.g. Inter or system font stack), 2­3 weights max, no decorative fonts.
         Status badges (Submitted / Under Review / Selected / etc.) as small, color-coded pills -- this is the one place color-coding earns its keep,
         since applicants will scan for it.
         No unnecessary icons or illustrations on data-entry screens -- save any illustration/branding moment for the dashboard's empty/welcome
         state only.
         Mobile-first: most applicants will use phones. Design the single-column mobile layout first, then adapt up to desktop -- not the reverse.

10. Suggested Build Order (MVP)

 1. Auth + user registration + application_number generation
 2. Applicant profile, next-of-kin, academic-record forms (React step flow)
 3. Programmes CRUD (admin) + programme listing (applicant)
 4. Payment module with PaymentServiceContract stub (Option A manual path first)
 5. Application create/submit + state machine + eligibility check (rule-based, per Section D of the form)
 6. Admin application list/filter/review + status changes
 7. SMS notification triggers on key state changes
 8. Reports (applications, payments) -- CSV first, PDF later
 9. Post-selection: document upload, admission letter generation
10. Audit log (wrap around steps 5­6 as they're built, not bolted on later)

11. Non-Functional Notes

Security: rate-limit auth endpoints, hash passwords (Laravel default bcrypt), validate all uploads server-side (mime + size), never trust client-
side eligibility checks alone -- recompute server-side before allowing submit.
Audit everything that changes application state -- who, when, from what status to what status.
Swahili + English: since applicant-facing copy is in Swahili, keep all user-facing strings in a translation file ( resources/lang or a JSON i18n file
on the React side) from day one, not hardcoded -- makes future English toggle or wording fixes trivial.
Environments: confirm hosting target early (local XAMPP dev is fine, but production will need a real MySQL/Postgres host + HTTPS for GePG
compliance if Option B is chosen later).
